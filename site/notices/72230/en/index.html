Title:
Corporate Security Response Guidelines for PHP Vulnerabilities (PHP2Shell)
Summary:
We are disseminating today's KISA announcement "Corporate Security Response Guidelines for PHP Vulnerabilities (PHP2Shell)". Please reply if you have any specific issues.
Body:
□ Overview
- Critical PHP vulnerabilities allow unauthenticated remote attackers to run commands on affected servers (CVE-2026-109618, CVE-2026-109619, CVSS 9.2). [1][2][3][5]
- Vulnerability information was leaked before the security update was distributed, and attempts at attacks are being reported, mainly by overseas security companies. If an attack is successful, it could lead to the installation of a remote control file (web shell), leakage of customer information, tampering with the website, or infiltration of the internal network.
- Companies using PHP are advised to take immediate action in accordance with the response guidelines below.
※ If a hosting company or equipment/solution manufacturer manages PHP, ask that provider whether it has implemented the measures below and request any outstanding action.
※ It is recommended to apply the patch after conducting a preliminary impact assessment and testing, as compatibility and stability issues with the existing system may cause service disruptions when the patch is applied.
□ Corporate Security Response Guidelines
1. Check the current status of PHP in use
- Check all public-facing websites and systems to see whether they run PHP and which versions they use.
- Include outsourced websites, older unmaintained sites, event and test servers, and administration pages.
- Verify the servers that are actually running in addition to consulting the asset inventory.
- Separately verify equipment and solutions with built-in PHP (e.g., network equipment management screens, installation packages for Windows that include PHP) as well as container images (e.g., Docker) obtained externally. [4]
2. Update to the latest version and restart
- Fixed versions: PHP 8.5.12, 8.4.27, 8.3.36, and 8.2.35 or later in the corresponding release branch, including updates provided by Linux distributions and vendors.
- Prioritize servers that are publicly accessible on the internet.
- After the update, be sure to restart all web services that run PHP (PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, LiteSpeed, etc.).
- If you do not restart, the previous version remaining in memory will continue to run, leaving the system still vulnerable.
- For container deployments, redeploy using updated images.
- After the update, check whether the PHP version actually used by the web service has changed.
※ Since the version identified by the command (php -v) and the version used by the web service may differ, if multiple PHP versions are installed on a single server, verify each version separately.
※ Since the version number of packages provided by Linux distributions and vendors may not change even after applying security patches, check the package changelog to confirm that the fixes for the CVEs are included.
3. Migrate PHP 8.1 and earlier to a supported version
- Migrate to a supported version because PHP 8.1 and earlier no longer receive official updates.
- Security support for PHP 8.2 is scheduled to end on 2026.12.31. Plan to migrate to PHP 8.3 or later.
- If migration will take time, temporarily apply security patches from your Linux distribution or long-term support (LTS) vendor, or the PHP Security Team's source patches for 7.4·8.0·8.1. Prepare a migration plan. [1]
- If there is no patch to apply, apply the temporary measures in Rule 4. If that is also difficult, consider blocking external access or temporarily suspending the service.
4. Apply temporary mitigations if you cannot update immediately
- Limit the request size (including requests without request size information) at the front end of PHP, such as web firewalls, web servers, and proxies, and block file upload (multipart) requests for services that do not require file uploads.
- If you are using a web firewall, check that the latest blocking rules have been applied.
- Restart all PHP processes after applying the official PHP runtime settings to php.ini, PHP-FPM pool settings, or web server settings. [1][2][3]
- session.upload_progress.enabled = 0 (Disable file upload progress display feature)
- memory_limit = -1 (Set as an administrator setting so that the program cannot change it, e.g., php_admin_value in the PHP-FPM pool)
- Set post_max_size to a low value (8M if uploads are not required, or 32M if they are). Keep upload_max_filesize smaller than post_max_size.
- For PHP 8.5, also set fatal_error_backtraces = 0.
※ Temporary measures do not completely prevent attacks, so updates are recommended.
- If even temporary measures are difficult to implement, we recommend considering blocking external access or temporarily suspending the service until the update is completed.
5. Review logs after updating
- Review all logs from 10.20 (the date the vulnerability information leaked) onward. Review earlier logs as well if available.
- Look for the following signs:
- Abnormally large requests to a PHP page followed by repeated server errors (HTTP 500)
- PHP program restart/abnormal termination (segfault) or out-of-memory error for unknown reasons
- Traces of the web server executing a command shell (sh, bash, etc.) or a file download tool
- Newly created or modified PHP files (webshells) in the web folder, upload folder, or temporary folder
- External scripts secretly added to the homepage or payment page
- Traces of a new connection from the web server to an unknown external address
※ Even if there are no issues in the records, security is not guaranteed, so updates and credential changes should be carried out together.
6. Changing Important Credentials
- This vulnerability can lead to the leakage of passwords, access authentication values (tokens), and external service integration keys (API keys) stored in the server's memory. [3]
- For servers that were exposed to the internet before the update, it is recommended to change the DB password, external service integration key, and administrator account password.
- For any server showing signs of compromise, rotate these credentials.
7. In the event of a breach, respond in the following order:
① Isolate the server by blocking external network access. Leave the server running.
② Report the incident through [Bohonara (https://boho.or.kr)] → [Report Security Incident] → [Report].
③ Preserve evidence, including server logs, the list of running processes, and network connection information.
※ When the server is restarted, any traces of the attack remaining in the memory will disappear, so evidence should be secured before updating and restarting.
④ Remediate by updating and restarting the server, removing web shells, and rotating credentials.
8. Avoid running PoCs with unclear sources
- Among the PoCs circulating on the internet, many are fake with hidden malware.
- Check versions and review logs to determine whether a system is vulnerable.
- If analysis is absolutely necessary, it should only be performed in an environment separate from the business network.
