PHP 보안취약점(PHP2Shell) 관련 기업 보안 대응 수칙
요약:
금일 KISA 공지 "PHP 보안취약점(PHP2Shell) 관련 기업 보안 대응 수칙" 전파드리오니, 특이사항 있으시면 회신 바랍니다.
본문:
□ 개요
- PHP에서 로그인 없이 외부에서 서버에 원하는 명령을 실행할 수 있는 치명적 보안 취약점 (CVE-2026-109618, CVE-2026-109619, CVSS 9.2) 발견 [1][2][3][5]
- 보안 업데이트 배포 전 취약점 정보가 유출되었고 해외 보안업체를 중심으로 공격 시도가 보고되고 있으며, 공격에 성공하면 원격조종 파일(웹셸) 설치, 고객정보 유출, 홈페이지 변조, 내부망 침투 등 가능
- PHP를 사용하는 기업은 아래 대응 수칙에 따라 즉시 조치할 것을 권고
※ 호스팅 업체나 장비·솔루션 제조사가 PHP를 관리하는 경우, 해당 업체에 아래 조치의 적용 여부를 확인하고 요청
※ 패치 적용 시 기존 시스템과의 호환성 및 안정성 문제로 서비스 장애가 발생할 수 있으므로, 사전 영향도 검토 및 테스트 후 적용 권고
□ 기업 보안 대응 수칙
1. 운영 중인 PHP 사용 현황 확인
- 인터넷에 공개된 모든 홈페이지와 시스템의 PHP 사용 여부와 버전 확인
- 외주 제작 사이트, 오래전에 만들어 두고 관리하지 않는 사이트, 이벤트·테스트 서버, 관리자 페이지 포함
- 자산 관리 목록에만 의존하지 말고, 실제 동작 중인 서버를 기준으로 확인
- PHP가 내장된 장비·솔루션(네트워크 장비 관리 화면, PHP가 포함된 윈도우용 설치 패키지 등)과 외부에서 받아 쓰는 컨테이너 이미지(도커 등)도 별도 확인 [4]
2. 최신 버전 업데이트 및 재시작
- 해결 버전: PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35 이상 (리눅스 배포판·제조사 제공 업데이트 포함)
- 인터넷에 공개된 서버부터 우선 조치
- 업데이트 후 PHP를 실행하는 모든 웹 서비스(PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, LiteSpeed 등)를 반드시 재시작
- 재시작하지 않으면 메모리에 남은 이전 버전이 계속 동작해 여전히 취약
- 컨테이너 환경은 신규 이미지 재배포
- 업데이트 후 웹 서비스가 실제로 사용하는 PHP의 버전이 바뀌었는지 확인
※ 명령어( php -v )로 확인되는 버전과 웹 서비스가 사용하는 버전이 다를 수 있으므로, 한 서버에 PHP가 여러 개 설치된 경우 각각 확인
※ 리눅스 배포판·제조사 제공 패키지는 보안 패치를 적용해도 버전 번호가 바뀌지 않을 수 있으므로, 패키지 변경 이력에서 CVE 반영 여부 확인
3. 구버전(PHP 8.1 이하)은 지원 버전으로 전환
- PHP 8.1 이하는 공식 업데이트가 제공되지 않으므로 지원 버전으로 전환
- PHP 8.2도 2026.12.31. 보안 지원이 종료될 예정이므로 8.3 이상 버전으로 전환 권장
- 전환에 시간이 걸리는 경우, 리눅스 배포판·장기지원(LTS) 업체가 제공하는 보안 패치 또는 PHP 보안팀이 공개한 7.4·8.0·8.1용 소스 패치를 임시로 적용하고 전환 계획 수립 [1]
- 적용할 패치가 없다면 수칙 4의 임시 조치를 적용하고, 그것도 어려우면 외부 접속 차단 또는 서비스 일시 중단 검토를 권고
4. 즉시 업데이트가 어려울 시 임시 조치 요망
- 웹 방화벽·웹 서버·프록시 등 PHP 앞단에서 요청 크기를 제한(요청 크기 정보가 없는 요청 포함)하고, 파일 업로드가 필요 없는 서비스는 파일 업로드(multipart) 요청을 차단
- 웹 방화벽을 이용 중이라면 최신 차단 규칙이 적용되었는지 확인
- PHP 공식 임시 설정을 php.ini, PHP-FPM pool 설정 또는 웹 서버 설정에 적용한 후 모든 PHP 프로세스 재시작 [1][2][3]
- session.upload_progress.enabled = 0 (파일 업로드 진행률 표시 기능 끄기)
- memory_limit = -1 (프로그램이 바꿀 수 없도록 관리자 설정으로 지정, 예: PHP-FPM pool의 php_admin_value)
- post_max_size 낮게 설정 (업로드가 필요 없으면 8M, 필요하면 32M 수준), upload_max_filesize는 post_max_size보다 작게 유지
- PHP 8.5 사용 시 fatal_error_backtraces = 0 추가
※ 임시 조치는 공격을 완전히 막지 못하므로, 업데이트 권고
- 임시 조치도 적용하기 어렵다면, 업데이트 전까지 외부 접속 차단 또는 서비스 일시 중단 검토를 권고
5. 업데이트 후 로그 점검
- 최소 10.20.(취약점 정보 유출일) 이후의 기록 전체를 점검하고, 가능하면 그 이전 기록까지 확인
- 주요 점검 항목
- PHP 페이지로 들어온 비정상적으로 큰 요청과 그 뒤에 반복된 서버 오류(HTTP 500)
- 원인을 알 수 없는 PHP 프로그램 재시작·비정상 종료(segfault)나 메모리 부족 오류
- 웹 서버가 명령 실행 프로그램(sh, bash 등)이나 파일 다운로드 도구를 실행한 흔적
- 웹 폴더, 업로드 폴더, 임시 폴더에 새로 생기거나 바뀐 PHP 파일(웹셸)
- 홈페이지나 결제 페이지에 몰래 추가된 외부 스크립트
- 웹 서버에서 알 수 없는 외부 주소로 새로 연결한 흔적
※ 기록상 이상이 없더라도 안전이 보장되지 않으므로, 업데이트와 인증정보 교체를 함께 진행
6. 중요 인증정보 교체
- 이번 취약점은 서버 메모리에 담긴 비밀번호, 접속 인증값(토큰), 외부 서비스 연동 키(API 키) 등을 유출시킬 수 있음 [3]
- 업데이트 전까지 인터넷에 노출되었던 서버는 DB 비밀번호, 외부 서비스 연동 키, 관리자 계정 비밀번호 교체 권장
- 침해 흔적이 발견된 서버는 반드시 교체
7. 침해사고 발생 시 아래 순서대로 대응
① 격리: 서버를 끄거나 재시작하지 말고, 네트워크에서 외부 접속만 차단
② 신고: [보호나라(https://boho.or.kr)] → [침해사고 신고] → [신고하기]를 통해 신고
③ 증거 확보: 서버 기록(로그), 실행 중인 프로그램 목록, 네트워크 연결 정보 보존
※ 서버를 재시작하면 메모리에 남은 공격 흔적이 사라지므로, 업데이트·재시작 전에 증거를 먼저 확보
④ 조치: 업데이트 및 재시작, 웹셸 제거, 인증정보 교체
8. 출처가 불분명한 PoC 실행 지양
- 인터넷에 유포되는 PoC 중에는 악성코드가 숨겨진 가짜가 많음
- 취약 여부는 PoC 실행 대신 버전 확인과 기록 점검으로 판단
- 분석이 꼭 필요한 경우 업무망과 분리된 환경에서만 수행
